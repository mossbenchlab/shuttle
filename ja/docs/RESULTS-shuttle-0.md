# Shuttle v0 → v4 — 核心が動く試作と最初の観察（2026-11-08）

位置づけ: 発明の段階の探索です。事前登録も公正な比較の設計もまだしていません。確かめたのは「仮説が働いているか、どこで詰まるか」だけです。

## 1. 作ったもの

- `shuttle.py`（Python、約 600 行）: スキーマ（型付きの表、キー、子表、文書部分）、状態、操作の言語、トランザクション（全部成功か全部失敗、同じ id の再送は同じ受領書、`at <版>` の前提）、期待（事後条件）、照会（count / show / get）、受領書。値は Weft next d6 の値のモデル。状態の全体は `materialize()` で文書として派生できる（WB-1 の正解の値との等価性の判定に使った）。
- 操作は1行1つ: `set <表> where <条件> : 列=値`、`add`（末尾、`after where` で位置指定、子表は親を条件で選ぶ）、`del`、`put <文書パス> = 値`、`expect ...`。条件は列の比較、`in`、`has`、`and/or/not`。文字列は行をまたいでよい（実際の改行が改行文字になる）。
- 受領書: `ok v=1 set:2 add:1 vid=<版の識別子12桁>`（v1。v0 は全状態のハッシュだった）、または `fail line N: <理由>` に修正の手がかり（列名の一覧、行数など）を添えて、何も適用しない。

## 3. 何が働いたか

- **AI の出力が、データの件数と無関係になった。** 6課題の操作は 3〜5 行で、表の行数（14〜24）に依存していない。書き直しでは、出力は行数に比例していた。
- **AI の入力も、件数からほぼ切り離された。** 渡したのは各表2行の例と文書部分だけ。宛先は条件（キー）で指すので、AI は該当行を見る必要がなかった。
- **変えない部分の書き写しの誤りは構造的に起きない。** 変えない行は AI の出力に現れない。ただし、条件を広く指定しすぎる誤りは残る（外部レビューの指摘で言い直した）。
- **意味の検証は実行系に残った。** 型（`status` はキーワード）、キーの重複、存在しない列・パス、`after where` の一意性、事後条件（`expect`）。失敗は受領書で1行を指して返り、何も適用されない。

## 4. どこで詰まったか（設計への反映）

- ソルバーは複数行の文字列を、`\n` ではなく実際の改行で書いた。行単位の言語ではこれが壊れたので、「閉じていない引用符があれば次の行に続く」規則にして解消した。
- 字句のエラーが受領書にならず例外で落ちた（直した）。閉じていない文字列と、文の後ろの余分な字句が通っていた（直した）。
- `set 7010 → :shipped` のような宛先の取り違えは、合法な命令なので実行系は止められない。`expect` を AI に書かせる習慣が、この種の誤りの検出になるかは未確認。

## 5. 限定

- 6課題、1モデル、1回。課題は WB-1 の修正課題で、Shuttle のために作ったものではない。
- 表の行数が小さい（14〜24）。件数への依存がないことは、大きな N で示していない。
- 件数が小さいので、機械側の時間差はまだ測っていない。
- 「JSON Patch で操作だけを書く」腕と比べていない（公正な比較は、形ができてから別に設計する）。

## 11. v5（v4 の外部レビューで区切りがついた後、同日）— 条件による一括更新と、照会を挟む仕事

v4 の時点で `set ... where <条件>` は一致した全行に効いていたが、(a) AI が現在値を知らないと書けない更新（「数量を 2 増やす」）が書けず、(b) 走査の 1 行あたりのコストが 5〜16 µs と重く、(c) 並べ替えがないため「最大のもの 1 件」のような仕事は全件を見るしかなかった。v5 では次を入れた。回帰テスト 84 件が通過。

言語の追加:
- `col += v` / `col -= v`：数は加減、リストは追加・除去（除去対象が無ければ失敗）。AI は現在値を知らなくてよい。
- `where true`：全行。
- `show ... order <col> [asc|desc]`：並べ替え（nil は最小値として扱う＝昇順で先頭、降順で末尾。種類の混在は失敗）。
- `set?` / `del?`：0 件一致を許す（受領書に `set:0`）。下の L3 で必要になった（§11.3）。

実装の変更（意味は変えていない）:
- 条件を文ごとに 1 回だけ Python の閉包に「コンパイル」し、定数側の正規化を事前に済ませる。等値は W.same（正準バイナリの同一性）と同じ結果を返すことを 22 種類の値の全組み合わせ（484 組）で確認。順序比較は従来と同じ結果で、**違いは 2 点**：(1) 型の混在（整数と日付など）や、定数側が nil の大小比較（`x < nil`）は、従来は黙って False または内部エラーだったものを「比較できない」の失敗にした。行の値が nil の場合は従来どおり「一致しない」で、失敗ではない。(2) 日付の大小は従来の正準文字列の辞書順から、時刻のある日付はオフセットを引いた瞬間の比較にした（`#...T03:04:05Z` と `#...T12:04:05+09:00` は同じ瞬間として `<=` が真、`<` が偽。等値は従来どおり正準表記の同一性なので偽）。日数計算は datetime と 20,000 件で一致。
- `set` の列解決と、定数代入 `=` の型検査を文ごとに 1 回に寄せた。相対代入も文ごとに閉包へ。取り消し記録は閉包からタプルに。

### 11.3 L3 で見えた設計の穴

L3 の最初のメッセージ `set orders where id = 3777 and status != :shipped : qty += 2` は正しい意図だが、0 件一致を執行器が失敗にしたため、解答側は `get` で確かめてから DONE とした（結果は正しいが 1 往復余計）。0 件一致を失敗にするのは条件の書き間違いを捕まえるためで、外したくない。そこで `set?` / `del?`（0 件を許す）を足し、失敗の hint に「ガード条件で 0 件が正しいなら `set?` と書け」を入れた。v5 の試行はこの変更前のカードで行ったので、表の数字は変更前のもの。

### 11.4 まだやっていないこと

- 条件走査は Python で O(n)。50 万行で 0.1〜0.7 s。列索引（等値・範囲）か Rust 移植で下げるかは、次に測る仕事の形で決める。
- 比較実験（JSON 全体書き換え / JSON Patch / Weft 一括 など）はまだ設計していない。形が固まってから、事前登録して行う。
- 解答側は 1 モデル・各 1 回。モデルを変えた試行（GPT、ローカルモデル）は未実施。

## 13. v5 r3（v5 r2 の外部レビューの後、同日）

### 14.2 見つかった不足（まだ実装していない。候補として記す）

## 15. v6 — 選択・集計の結果を機械の中で次の処理につなぐ（探索 M の外部レビューの後、同日）

### 17.1 小さいモデルが露わにした執行器の不具合（3 件、修正済み → v6 r3、回帰テスト 140 件）

1. **日付と日時の大小比較**（L6.h、P1 相当）。解答側が `due >= #2026-03-01T00:00:00Z and due < #2026-04-01T00:00:00Z` と書いた。列は日付のみ。執行器は日付のみを「同じ瞬間の日時より前」に並べていたため、3 月 1 日（9 件）が外れ、4 月 1 日（15 件）が入り、`expect` も通って**黙って誤った状態**になった（ダイジェスト不一致）。修正：日付のみと日時の大小比較は失敗にし、「列は日付なので境界も日付で書け」と案内する。並べ替えでも混在は失敗。
2. **tx id の使い回し**（M5.h、P1 相当）。解答側が読み取り専用のメッセージに `tx mark-top-review at 0` と付け、次の書き込みにも同じ id を付けた。執行器は同じ id を「再送」とみなして古い受領書を返し、**書き込みを黙って捨てた**。修正：同じ id でも本文が違えば失敗（「id は 1 メッセージの名前。再送のときだけ同じ id」）。本文が同じなら従来どおり再送扱い。

### 18.2 会話ログを読んで分かったこと → v6 r5（エラー文の改善）

M4〜M6 の events.jsonl（モデルの全返答・全受領書）を読んだ。4B の失敗の大半は、**小さいモデルが書きがちな 4 つの書き方の揺れに対して、執行器のエラー文が原因と直し方を言っていなかった**ことにある。Haiku 5.5 はエラー文が曖昧でも 1 回で自己修正したが（§17）、4B はエラー文に頼る。

| 4B が書いたもの | 旧エラー文 | 回数 | r5 の挙動 |
|---|---|---|---|
| `where … :qty=0`／`:tags+=:x`（代入の前の `:` を詰めた） | `expected :, got ':qty'` | M4 で 2 回 | 空白の有無だけで意味は一つなので**受理**（`: qty=0` と同じ） |
| `:status=:review, :note="top"`（列名に `:`） | `expected :, got ':status'` | M5 で 4 通（4〜7 通目）；その後は途中切れ 2 通と、同じ id による旧受領書の再送 3 通 | `':note' is a keyword value; a column name has no colon` ＋ `write note=...` |
| `set … where id=31000 status=:review`（`:` 抜け） | `expected :, got 'status'` | M5 で 1 回 | `expected ':' before the values` ＋ 書式の案内 |
| `tx 0 at 0 set …`（ヘッダと操作を 1 行に） | `unexpected 'set' after the tx header` | M5 で 1 回 | ＋ `the tx header is a line of its own` |
| `due:#2026-12-01`（`=` の代わりに `:`） | `not a value: ':#2026-12-01'` | M6 で 2 回 | `` `due:` — in a named add write `due=#2026-12-01` `` |
| `{sku:::p01, qty:2}`（マップの `key: value` の空白なし） | `expected a value, got ':'` | M6 で 3 回 | ＋ `in a map write key: value with one colon and a space; sku: :p01` |
| stale 後に版だけ差し替えて同じ行を狙う | `fail stale: you assumed version 0, current is 1` | M5 | ＋ `Read again before writing … and guard the write with the condition you relied on` |

受理したのは詰めた `:` だけ（意味が一つに決まる）。それ以外は構文を緩めず、エラー文に原因と書き直し例を入れた。4B の実際のメッセージをそのまま r5 に通し、それぞれ上の文が出ることを確認（テストに追加）。回帰テスト 157 件。

執行器のエラー文が正確で、4B が次の 1 通で直せたのは：`any orders.lines`（→ `children: lines`）、`any orders`（→ `lines has no child tables`）。子表追加の `where` 欠けのエラー文も正確だったが、M6 の最後の応答だったので直せたかは未観測。

残りは思考出力の途中切れ（M5 で 2 回、M6 で 6 回、各 8,192 tok）で、これはモデル設定の話。ランナー側に思考オフが追加されたので、r5 のカード・執行器で M4〜M6 を再測定する。

### 18.3 r5・思考オフで再測定（Qwen3.5-4B、M4〜M6）→ 不合格 3/3、v6 r6

r5 の執行器・カードで、思考出力を切って M4〜M6 を再測定した（run.json の SHA が r5 と一致することをレビュー側が確認）。途中切れは 0、解答時間は 3 課題合計 919 秒 → 27.7 秒。しかし 3 件とも不合格。**失敗の中心は書式ではなく、対象の選び方と、失敗後の状態の読み違い**だった。§18.2 で「失敗の大半はエラー文」と書いたのは言い過ぎで、エラー文で直るのは書式の揺れまで。

| 課題 | 通数 | 何が起きたか | 執行器側で直せること |
|---|---|---|---|
| M4 | 5 | `set orders.lines where orders.status=:unpaid and sku=:p03` → エラー文が「no column 'orders.status' … hint: columns: sku, qty, amount」と**子の列しか挙げなかった**ため、モデルは未払い条件を削り、全状態の :p03 明細 24,927 行を更新した（受領書の set:37260 は、札を付けた親 12,333 行との合計） | hint が誤誘導。親の列も列挙し「`orders.status` ではなく `status`」と言う（r6） |
| M5 | 6 | 照会せず `set orders where status=:unpaid : status=:review, note="top"` で 30,051 件を変更。競合の回復も未検証 | エラー文では止まらない（正しい構文で、意図と違うだけ）。言語に「上位 1 件を直接更新する」書き方が無く、照会→id 転記を強いていた → `set … order total desc limit 1 : …` を追加（r6）。これで通るかは別モデルで要確認 |
| M6 | 12 | `add` に total を書かず「missing orders.total (no default)」→ 存在しない行への `set` を試み、`set?` の受領書に出た全明細の合計（18,948,216.68m）を total にしようとし、同じ add を 5 回繰り返した | hint が足りない。「既定値のない列は add の中に書く（`total=0m` でよい）。同じメッセージの次の行で更新できる」を hint に入れた（r6） |

v6 r6 の変更（回帰テスト 165 件）:
- 子表の条件で親の列が見つからないときの hint：子の列と親の列を両方列挙し、`orders.status` なら「`status` と書け」と言う。
- 名前付き add で既定値のない列が抜けたときの hint：その列の型に合う例（`total=0m`）と、同じメッセージの後の行で更新できることを言う。
- **`set/del … where <cond> order <col> [asc|desc] limit n : …`**：その順で先頭 n 行だけに適用。n 行目と n+1 行目が同値なら失敗（どちらを選ぶか決められないため）。`order` 無しの `limit n` は表の順で先頭 n 行。照会→id 転記→書き込みが 1 メッセージになり、版の衝突の窓も消える。

M5 の「30,051 件を変えた」は執行器が正しく実行した結果で、止める根拠が言語側にない。「1 件のつもりが大量」を防ぐなら、解答側が `expect count … = 1` を書くか、`limit 1` を使うかで、どちらもカードに載っている。これ以上は執行器の責務ではなく解答側の能力。
